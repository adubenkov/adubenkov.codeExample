# Кампания по чистке тестов

Кампания чистит всю тестовую поверхность одной подсистемы одним PR: модуль,
пакет или зону из AGENTS.md. Планка ценности, планка удержания, досье
кандидата и проверка из [SKILL.md](SKILL.md) действуют на каждом
направлении. Здесь — порядок работы и уроки полной кампании. Каждый шаг
кончается своим критерием готовности; следующий раньше не начинается.

Кампания — работа менеджера: направления раздаются отдельным экземплярам
ролей, у самой роли исполнителя `Agent` в `tools:` может не быть. Больше
~400 изменённых строк — обоснование размера в теле PR обязательно
(docs/TEAM.md, `code-reviewer`), иначе BLOCK «разбей PR».

## 1. База

Запиши число строк тестов и тестовой обвязки подсистемы и результат каждого
тестового файла на зафиксированном SHA `main`. Провалы на базе — отдельным
списком: в исходной кампании все три оказались настоящими багами доставки, а
не устаревшими тестами.

Готово, когда у каждого тестового файла в охвате записан результат на базе.

## 2. Направления и опись

Раздели поверхность на **направления** по границам продуктовых владельцев, а
не по префиксам файлов (учётные записи, команды, входящие, исходящие,
хранение, транспорт, общее, обвязка, живые сценарии). Включи случаи подсистемы
на общих границах ядра и тесты её живой проверки.

Готово, когда каждый тестовый файл и сценарий подсистемы принадлежит ровно
одному направлению.

## 3. Ведомость по направлению — только чтение

Каждое направление — своему экземпляру роли только на чтение. Он читает каждый
назначенный тест целиком, включая таблицы параметров, и продуктовых владельцев
с точками входа, вызывающими, историей и маршрутом в `ci`. Каждое объявление
теста попадает в письменную **ведомость** с одной отметкой. Параметризованный
тест — одно объявление, если строкам не нужны разные отметки; иначе отметка
на строку.

- `R` — оставить; назвать контракт и баг, который тест ловит. Тест, который
  лишь переезжает в файл с лучшим именем, остаётся `R` с пометкой о переезде;
- `F` — контракт оставить, проверку починить: например, пустой отрицательный
  контроль, проходящий, когда пропал лишь один из нескольких элементов;
- `C` — свести; назвать владельца, который первым примет проверку: соседнюю
  строку таблицы, более сильный набор на границе, общего владельца в другом
  пакете;
- `D` — удалить; назвать оставшееся доказательство или почему контракта нет.

Суди тест по проверкам, а не по имени: тест с именем «закрывает окно
прогресса» проверял, что окно НЕ закрыто.

Готово, когда у каждого объявления направления есть отметка и строка
доказательства.

## 4. План слоёв по направлению

Ведомость — вход, а не список правок. Второй проход на чтение ищет лишний
**слой**: в исходной кампании несколько наборов гоняли один и тот же общий
компоновщик через один мок — рядом с более сильными наборами на настоящем
потоке и HTTP-фикстурах. Для каждого контракта назови **хранителя**. Лучше
настоящая граница транспорта с поддельной сетью, чем мок соседа. Ошибки
ведомости, найденные этим проходом, исправь.

Готово, когда план направления называет снимаемые файлы, хранителя каждого
контракта, проверки для переноса в хранителей и открываемые тестовые швы
продуктового кода.

## 5. Переход

Правь по направлению за раз. Правки общей обвязки и вспомогательных файлов —
через одного владельца, последовательно. С каждым направлением убирай
открывшиеся тестовые швы: параметры внедрения, геттеры, экспорт сброса,
слои косвенности. Перенесённые наборы — в маршрут `ci`. Долговременные правила
владения тестами, выведенные из ошибок, которые кампания действительно нашла, —
в AGENTS.md проекта (правит человек или по его поручению).

Готово, когда каждый план применён и хранители каждого направления зелёные.

## 6. Проверка сохранности

До заявления о готовности независимые проверяющие, по одному на группу
границ, сверяют удалённое покрытие с хранителями: ищут контракты, лишившиеся
единственного доказательства, и новые проверки, которые не могут упасть
(строка отказа, до которой продуктовый код не доходит). В исходной кампании
такая проверка нашла девять настоящих дыр и одну недостижимую проверку.

Для каждого восстановленного контракта сделай одну намеренную **мутацию**
продуктового владельца и убедись, что хранитель краснеет. Затем верни
исходник байт в байт (`git diff` пуст).

Готово, когда каждая найденная дыра закрыта или отвергнута с доказательством
по исходнику, и у каждого восстановленного контракта есть пойманная мутация.

## 7. Дефекты продукта

Провал базы, доживший до хранителя, — баг. Чини его у владельца отдельным
коммитом и докажи на настоящем пользовательском пути **контрольным** прогоном:
откат исправления показывает старое поведение. Посторонние расхождения
продукта — строками в docs/specs/BACKLOG.md, не в кампанию.

Готово, когда у каждого исправленного дефекта есть красный контроль и зелёный
кандидат на одной обвязке.

## 8. Сведение и передача

Кампания переживает много коммитов `main`. Вливай `main` в ветку, а не
перебазируй длинную многокоммитную кампанию. Если `main` изменил файл,
который кампания удалила, — удаление остаётся, а новый контракт переносится в
хранителя; проверь, что у каждой новой регрессии из `main` есть дом. Прогони
весь набор подсистемы и живую проверку на сведённой вершине.

Отчёт — по [SKILL.md](SKILL.md), плюс:

- строки тестов и обвязки на базе и в итоге, продукт отдельно;
- направления, снятые слои и хранители;
- найденные дыры сохранности и их мутации;
- дефекты продукта с контрольным и кандидатным доказательством.
