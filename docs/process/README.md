# Наблюдение за процессом

> **Канон этого документа живёт в репозитории процесса** — `dev-process/docs/observability.md`
> (по умолчанию `~/Coding/Pet/dev-process`). Там же лежат и сами инструменты,
> в `tools/`; команды `./scripts/…` ниже — мосты в проекте и работают как прежде.
> Копия здесь нужна потому, что агент читает только внутри рабочего каталога.
> Правишь одну — правь обе; расхождение показывает `dev-process/bin/process-doctor`.

Каталог для данных о САМОМ процессе разработки — не о продукте. Здесь живут
журнал прогонов агентов (С52/W1), страница наблюдения (С52/W2) и её сетевой
кэш.

| файл | что это | чем обновляется |
| --- | --- | --- |
| `agent-runs.jsonl` | журнал прогонов подагентов | `./scripts/agent-runs-journal.py` |
| `dashboard.html` | страница наблюдения за процессом | `./scripts/process-dashboard.py` |
| `dashboard-cache.json` | сетевая часть страницы (гейт + CI) | `./scripts/process-dashboard.py --refresh` |

Все три файла обновляет и коммитит тик `scripts/process-sync.sh` (launchd,
дважды в сутки) — команды выше нужны, только если хочется увидеть состояние
прямо сейчас. См. «Автообновление».

## `agent-runs.jsonl` — журнал прогонов агентов

Строка на каждый запуск подагента: роль, задача, времена, токены, инструменты,
скиллы, ветка, исход. Формат — JSONL, одна запись = один прогон.

```sh
./scripts/agent-runs-journal.py              # собрать/дописать журнал
./scripts/agent-runs-journal.py --summary    # то же + агрегат по ролям
./scripts/agent-runs-journal.py --summary --no-write   # только посмотреть
./scripts/agent-runs-journal.py --self-test  # проверить сам скрипт
```

Полный прогон по 641 записи занимает ~2 c, так что чинить инкрементальность
пока нечего.

### Почему журнал лежит в репозитории

Источник данных — каталог сессий Claude Code (`~/.claude/projects/…`), он живёт
на машине PO и рано или поздно чистится. Журнал в репозитории — единственный
долгоживущий след: он переживает чистку сессий, доступен CI и служит источником
для страницы наблюдения. Прецедент такого артефакта в репозитории —
`docs/sprints/artifacts/s36-corpus/corpus.jsonl`; но тот привязан к одному
спринту, а этот накопительный и сквозной, поэтому лежит в `docs/process/`, а не
в `docs/sprints/artifacts/`.

Ловушка git: глобальный `~/.config/git/ignore` содержит `**/docs/`, репозиторий
обходит это негацией в `.gitignore`. Новый каталог `docs/process/` проверен
фактом — `git check-ignore -v docs/process/agent-runs.jsonl` не даёт совпадений.

### Приватность — жёстко

В журнал попадают ТОЛЬКО агрегаты: роль, времена, счётчики, ИМЕНА инструментов
и скиллов, ветка. Тела промптов, отчётов и сообщений не попадают ни в каком
виде. Единственная строка задачи — `description` из meta, она и задумана как
короткий ярлык прогона.

Это не обещание в комментарии: `_assert_aggregates_only()` роняет сборку, если
в записи появилась строка с переводом строки или длиннее 300 символов, — то есть
если кто-то однажды дописал в журнал кусок текста сообщения. Проверка покрыта
`--self-test`.

### Исход — эвристика, и она так и названа

В данных нет поля «чем кончилось». Исход выводится из формы завершающего
сообщения, поэтому у каждой записи стоит `outcome_is_heuristic: true`, метод и
уверенность — потребитель обязан видеть, на чём держится вывод.

| метод | уверенность | что засчитывает |
| --- | --- | --- |
| `meta.stopped_by_user` | high | явная остановка человеком — факт из meta |
| `gate_anchor_first_line` | high | ПОЛНЫЙ контракт `.github/workflows/gate.yml`: первая строка целиком `GATE: APPROVE|BLOCK` + вторая `sha: <hex>`; ТОЛЬКО роль `code-reviewer` — у прочих даже полный контракт это реле чужого вердикта (аудит №4) |
| `gate_anchor_no_sha` | medium | строгая первая строка без валидной sha-строки — gate.yml такой вердикт не засчитает; ТОЛЬКО роль `code-reviewer` |
| `qa_anchor_first_line` | high | первая строка целиком `QA: PASS|FAIL` — контракт приёмки (решение PO 2026-08-28); ТОЛЬКО роль `qa` |
| `gate_anchor_inline` | medium | якорь гейта не в канонической позиции; засчитывается ТОЛЬКО роли `code-reviewer` |
| `no_closing_report` | medium | прогон оборвался на вызове инструмента — закрывающего отчёта не было |
| `verdict_word` | low | голое слово APPROVE/BLOCK в отчёте ревьюера |
| `failure_lexicon` | low | узкий лексикон провала в НАЧАЛЕ первой строки отчёта |
| `final_report` / `final_report_after_api_error` | medium / low | отчёт есть, признаков провала нет |
| `no_final_report` | low | ни отчёта, ни признаков — `unknown` |

Порядок намеренный: `no_closing_report` стоит ВЫШЕ слабых словесных признаков.
Прогон без закрывающего отчёта — это дефект процесса, и прятать его за словом
из середины переписки нельзя.

Цитата контракта в прозе — не вердикт: без ограничения по роли `Explore`,
`devops` и `general-purpose` получали чужой «approve» (проверено на живых
данных, 5 записей).

### Чего в журнале НЕТ (честные ограничения)

- **Ведущей сессии.** Источник — только `subagents/`, то есть подагенты.
  Время и токены самого оркестратора остаются за кадром: это не «стоимость
  волны», а «стоимость делегированной работы».
- **Твёрдого исхода.** На живых данных `high` — 33 записи из 641; остальное
  `medium`/`low`. Хочется твёрдо — нужен момент записи в конце прогона
  (хук `SubagentStop`), это следующая порция.
- **Связи с PR.** `pr_hint` вытащен регуляркой из `description` (формы «#247» и
  «PR 232») и заполнен у 242 записей из 641; номер issue в такой же форме туда
  тоже попадёт. Влит PR или нет — журнал не знает, это GitHub API.
- **Ветки работы.** `git_branch` — это ветка *cwd* прогона, а не та, в которой
  он работал: агенты ходят в слоты через `git -C <worktree>`, не меняя cwd,
  поэтому у 421 записи стоит `main`. Настоящую ветку знает только
  `worktree_branch`, и он заполнен у 48 записей — тех, кому worktree выдал
  сам харнесс.
- **Денег.** Модель известна (`models`), тариф — нет; в токенах, а не в рублях.
- **Истории до 2026-07-15.** Раньше каталог сессий не сохранялся.
- **Возможности перепроверить старое.** Записи, чей транскрипт уже вычищен из
  `~/.claude`, журнал сохраняет, но пересчитать их заново нельзя. Ради этого
  журнал и накопительный.

### Идемпотентность журнала

Ключ — `run_id`. Существующий журнал читается, разобранные прогоны его
дополняют и обновляют, файл переписывается целиком в стабильном порядке.
Повторный прогон без новых данных даёт побайтово тот же файл (проверено
`--self-test`). Живой, ещё не закончившийся прогон при каждом запуске
обновляется — это норма, а не дубль: записей всё равно ровно столько, сколько
прогонов.

## `dashboard.html` — страница наблюдения за процессом

Один самодостаточный HTML-файл: какая стадия процесса идёт прямо сейчас, над чем
работа, во что обходятся прогоны агентов, какие идеи PO ждут очереди, ловит ли
ревью-гейт и сколько длится CI. Открывается двойным кликом — ни сети, ни сервера
не нужно.

```sh
./scripts/process-dashboard.py              # пересобрать страницу из файлов (офлайн, ~1 c)
./scripts/process-dashboard.py --refresh    # то же + обновить сетевой кэш (нужны gh и сеть)
./scripts/process-dashboard.py --all-projects  # журнал по ВСЕМ проектам → ~/.claude/process/
./scripts/process-dashboard.py --self-test  # проверить разбор источников
```

Руками порядок такой: сначала `agent-runs-journal.py` (журнал), затем
`process-dashboard.py --refresh` (страница). Но обычно этого делать не нужно —
см. «Автообновление» ниже.

## Автообновление — `scripts/process-sync.sh` (С52/W3)

Задача PO 2026-08-24: «сделай автоматический мониторинг». До неё страница
обновлялась только руками, а значит устаревала ровно тогда, когда на неё стоило
смотреть.

```sh
./scripts/process-sync.sh             # тик: журнал + страница, коммит и push при изменениях
./scripts/process-sync.sh --dry-run   # то же без коммита и push
./scripts/process-sync.sh --state     # что было в последний тик (read-only)
./scripts/process-sync.sh --self-test # проверить сам скрипт на фикстуре
```

**Механизм — launchd-агент проекта-донора (`com.<донор>.process-sync`) на Mac PO**, дважды
в сутки (08:30 и 20:30; машина спала — launchd догоняет на пробуждении).
Plist — в репозитории проекта-донора (`scripts/launchd/…plist`),
установка и прогон руками — в шапке plist. Лог:
`~/Library/Logs/<донор>-process-sync.log`.

**Почему не GitHub Actions.** Журнал строится из `~/.claude/projects/**` —
локального диска. Облачный раннер их не видит; остаются self-hosted раннеры на
этом же Mac или launchd. Раннеры отпадают **по природе отказа**: их штатно
останавливают между спринтами (docs/CICD.md «Self-hosted раннеры»), и
расписанная джоба тогда не падает, а тихо висит в очереди сутки и отменяется —
ровно та тихая остановка, которую задача обязана исключить. launchd от раннеров
не зависит. Прецедент механизма — тик уборки донора (ежедневный тик
уборки, 04:15), новых сущностей не заводится.

**Тик безобиден для чекаута PO.** Он работает в собственном рабочем дереве
в собственном чекауте тика (detached на `origin/main`) и пушит ровно
свой коммит — `HEAD:main`. Незакоммиченная работа в основном чекауте, чужая
ветка на HEAD и чужие локальные коммиты его не касаются.

**Вхолостую не молотит.** Страница печатает время сборки и возрасты («3 ч
назад»), поэтому её байты меняются на каждом прогоне — гейт «изменился ли файл»
давал бы мусорный коммит дважды в сутки. Решение принимается по ДАННЫМ, и
источников три: журнал прогонов, сетевой кэш (метрики гейта и исходы CI — из
него страница узнаёт, например, что дрейф-чек VPS покраснел) и сам
`origin/main`. Ни один не изменился — тик заканчивается без коммита (в логе
строка «данных не прибавилось»), а пересобранная страница выбрасывается.

Кэш при этом пересобирается **всегда**, даже когда журнал стоит. Иначе
получалась бы дыра ровно в главном сценарии: новости CI приходят как раз
в тихие дни — ночной дрейф-чек покраснел, агентов никто не запускал, `main` не
двигался, — и гейт «только по журналу» проспал бы их до следующей волны.

**Падает громко.** Ошибка = ненулевой код + строка в логе + системное
уведомление на Mac. Состояние последнего тика — `state.tsv` рядом с рабочим
деревом; его печатает `--state`, и он же попадает в вывод
`scripts/status-snapshot.sh` на каждой вехе, поэтому «агент выгружен» и «тика не
было третьи сутки» видит человек, а не только лог. Тик, упавший на push'е,
не затирает память о последнем успехе — иначе `--state` соврал бы.

**Офлайн — не поломка.** Ноутбук без сети — обычное состояние, и уведомление
на каждое утро в отъезде приучило бы жать «пропустить». `git fetch` не прошёл →
статус `offline`, ноль в коде возврата, тишина. Поэтому тревог в `--state`
ДВЕ и они про разное: «тика не было больше 26 ч» ловит выгруженный агент и
выключенную машину, «успешного тика не было больше 26 ч» — тик, который
исправно бежит и исправно ничего не может (вечный офлайн, упавший push).
Без второй проверки вечный офлайн выглядел бы здоровьем: `last_run`
обновляется, а страница стоит.

**Чего схема НЕ ловит — честно.** Если агент выгружен, а Mac выключен, никто не
крикнет в ту же секунду: некому. Ловится это при следующем взгляде человека —
строкой в `status-snapshot.sh` на вехе и тревогами `--state` (возраст тика или
возраст последнего успеха больше 26 ч; успеха не было ни разу). Отметка
«Собрано» на самой странице сигналом живости **не является**: она одинаково
стареет и когда тик умер, и когда данные просто не менялись, — и подвал
страницы теперь говорит это прямо, вместо того чтобы обещать несуществующую
проверку. Облачного сторожа за «тишиной» нет намеренно: он требовал бы
heartbeat-коммита каждый тик — то есть ровно того молочения вхолостую, которое
запрещено выше.

### Инструмент про процесс, а не про проект

Страница делится надвое, и это не косметика, а условие переносимости:

- **Универсальная часть** — стадии, «идёт сейчас», экономика, здоровье. Считается
  из журнала прогонов, который живёт в каталоге сессий Claude Code и про
  репозиторий ничего не знает. Проект в ней — **измерение** (`project_dir` в
  записи), а не рамка: журналов можно передать несколько
  (`--journal a.jsonl --journal b.jsonl`), и в разрезе будут все проекты сразу.
- **Проектная часть** — спринт и порции, идеи PO, метрики ревью-гейта, CI. Это
  то, что физически лежит в репозитории, поэтому репозиторий — **параметр**:
  `--project <путь>`. Нет проекта (`--project ''`) или нет его файлов — блоки
  честно пустые, остальная страница строится.

Направить на другой проект — значит выполнить
`./scripts/process-dashboard.py --project ~/Coding/Другой --journal <его журнал>`;
переписывать в генераторе нечего.

`--all-projects` собирает журнал по ВСЕМ каталогам сессий (тем же скриптом W1,
с широким префиксом) и кладёт журнал и страницу в `~/.claude/process/` — **вне
репозитория**: прогоны чужих проектов не место в истории одного из них.

### Откуда берётся каждый блок

| блок страницы | источник | нужен проект? |
| --- | --- | --- |
| Стадия процесса (конвейер, «идёт сейчас») | журнал прогонов + таблица `STAGES` в генераторе | нет |
| Сейчас в работе | `docs/STATUS.md` + паспорт активного спринта из `docs/sprints/` | да |
| Экономика | журнал прогонов (разрез по проектам — из поля `project_dir`) | нет |
| Идеи и раскладка | `docs/specs/BACKLOG.md` (записи «ИДЕЯ PO …» / «РЕШЕНИЕ PO …») | да |
| Здоровье процесса | журнал + `scripts/process-metrics.sh` (через кэш) | частично |
| Прогоны CI | `gh run list` (через кэш) | да |

Активным спринтом считается паспорт БЕЗ пометки `CLOSED` с самой поздней датой
старта: слово `Active` осталось в шапках старых паспортов, и выбор по слову
показывал бы позапрошлую волну. Сколько таких паспортов и какие идут следом —
написано на самой странице.

### Стадия — из ролей, а не из самоотчётов

Роль прогона → стадия по таблице `STAGES` в генераторе (её и правят, когда
меняется процесс): `Explore` → разведка, `analyst` → требования, `techlead` →
стандарты, `server-dev`/`client-dev` → разработка, `code-reviewer`/`reviewer` →
ревью, `qa` → приёмка, `devops` → инфраструктура, `docs` → документы, `manager`
→ координация. Роль вне таблицы попадает в «прочее» — это сигнал дополнить
таблицу, а не спрятать роль.

Спрашивать у агентов, на какой они стадии, бессмысленно: самоотчёт расходится с
реальностью — это ровно та болезнь, которую страница должна показывать.

### «Идёт сейчас» — пока эвристика, и она названа

Твёрдого признака в данных нет: журнал строится по транскриптам, и у идущего
прогона от законченного отличается только то, что последнее событие — вызов
инструмента, и оно свежее. Правило: нет `finished_at` **либо** прогон оборвался
на инструменте и последняя отметка моложе 120 минут. На странице этот блок
помечен «эвристика» и объясняет правило.

Заменить эвристику фактом можно, не трогая страницу: `--live-from FILE` читает
список живых прогонов из файла (его напишет хук завершения субагента — следующая
порция), и блок начинает называть источник фактом.

### Правила, которые не дают странице соврать

1. Каждый блок собран из файла, журнала или API — ручной прозы на странице нет.
2. Выведенные данные (исход прогона, «идёт сейчас», номер PR из `pr_hint`,
   раскладка по окнам волн) помечены значком «эвристика» прямо на странице, а не
   только в коде.
3. Чего в источнике нет — того нет и на странице: блок честно пишет «нет
   данных» и называет команду, которая их добудет.
4. Цитаты из доков экранируются: строка из `STATUS.md` не может подменить
   разметку страницы (проверяется `--self-test`).

### Сеть — необязательна

`process-metrics.sh` и длительности прогонов CI требуют `gh` и сети, поэтому
собираются только по `--refresh` и складываются в `dashboard-cache.json`
(в нём — уже посчитанные агрегаты, а не сырые ответы API). Обычная сборка
читает кэш и работает офлайн; кэша нет — эти два блока пустые, страница всё
равно строится. У сетевых чисел на странице стоит момент сбора и окно — видно,
если кэш устарел.

### Чего на странице НЕТ

- **Стоимости в деньгах.** Тарифов в журнале нет — экономика в токенах.
- **Времени оркестратора.** Ограничение журнала (см. выше), а не страницы.
- **Реального времени.** «Идёт сейчас» — состояние на момент сборки страницы, а
  не живая лента: страница статическая и сама себя не обновляет. Тик
  `process-sync.sh` пересобирает её дважды в сутки; нужен взгляд «прямо
  сейчас» — запусти его руками.
- **Твёрдой привязки «идея → спринт».** В `BACKLOG.md` раскладка описана
  прозой; страница показывает все упоминания вида «С50» и «#404», найденные в
  теле записи, и честно говорит, что это не привязка.
- **Автовыката.** Страница локальная: журнал показывает внутреннюю кухню, на
  публичный домен её пока не вешаем. Выкат рядом с `/miniapp/` механически
  возможен (`deploy-miniapp.yml`) — это отдельное решение PO.
