# Сервис: GitHub через gh

Конвенции работы с GitHub для всех ролей. Канон —
`dev-process/stacks/github.md`; копия в проекте — `docs/stack/github.md`.

## Канал — только gh, тексты — только body-file

- PR, комментарии, issue — через `gh` (`pr create/view/diff/checks/comment`,
  `issue create`), плоскими одиночными командами.
- Любой многострочный текст (тело PR, комментарий, issue) — сначала Write
  в файл в скратчпаде, затем `--body-file <файл>`: markdown с backticks
  инлайном в команде триггерит permission-промпт у владельца.

## Что в этом окружении не работает (проверено, не догадки)

- **Комментарии читаются через API или `--json`, но не флагом `--comments`.**
  `gh pr view <N> --comments` и `gh issue view <N> --comments` печатают только
  предупреждение о прекращении поддержки Projects classic и больше ничего
  (находка проекта, проверено 2026-09-03). Работают:
  `gh pr view <N> --json comments --jq '.comments[].body'` и
  `gh api repos/<владелец>/<репо>/issues/<N>/comments --jq '.[].body'`.
- **Тело PR правится через API, а не `gh pr edit`.** `gh pr edit <N> --body-file`
  падает на той же ошибке Projects classic и тела не меняет. Работает
  `gh api -X PATCH repos/<владелец>/<репо>/pulls/<N> -F body=@<файл>`.
- **`main` уехал под ждущим PR — ветку доводят СЛИЯНИЕМ, не ребейзом.** Ребейз
  переписывает уже опубликованные коммиты, а запушить их можно только
  force-push, который режется хуком. Это был тупик регламента: он говорил про
  ребейзы и одновременно запрещал единственный способ их отправить. Выход —
  `git -C <слот> merge origin/main`, затем обычный push.

## Ветки и история

- Ветка порции — `task/<слаг>`, режется от `origin/main`. Сразу после создания,
  ДО первого своего коммита, проверь одной строкой, что вершина ветки и есть
  `origin/main`:
  `test "$(git -C <слот> rev-parse HEAD)" = "$(git -C <слот> rev-parse origin/main)"`.
  Две формы, которые для этого НЕ годятся, названы здесь, чтобы их не
  изобретали заново. «merge-base непуст» (правило до 2026-09-20) ловит только
  ветку от чужой истории. «merge-base равен origin/main» не ловит ничего сверх
  того: если локальный main опережает origin, merge-base и ЕСТЬ `origin/main`.
  Случай, ради которого правило переписано, — ветка от опередившего локального
  main: она везёт непрошеные коммиты в базе, где их не видно ни в диффе, ни
  в категории PR. Равенство вершин живёт один миг — первый свой коммит ломает
  его законно; дальше инвариант держит запрет коммитить в локальный main (хук).
- Push после КАЖДОГО коммита (правило P3: обрыв сессии не теряет работу).
- Force-push и shallow-fetch запрещены всем — механически, хуком
  (`dev-process/hooks/`); история правится только новыми коммитами.
  Почему shallow смертелен именно здесь: worktree-слоты делят ОДНУ объектную
  базу git — запись в `.git/shallow` обрезает родителей у SHA сразу всем, и
  живая ветка выглядит «сиротой без merge-base» (в С32 это стоило ложного
  диагноза «нужен replay с нуля» на PR #233). Лечение уже случившегося —
  `git fetch --unshallow`.

## Две джобы, два разных смысла: `gate` и `ci`

- `gate` — commit status ПО ВЕРДИКТУ ревью, тестов не гоняет. Эталон джобы —
  `dev-process/templates/gate.yml`, копия проекта — `.github/workflows/gate.yml`.
  На непродуктовых PR статуса не выставляет — вердикта там не бывает. Держит
  это не только `paths-ignore` (он действует лишь на `pull_request`), но и шаг
  по файлам PR из API: у `issue_comment` фильтра путей нет по устройству GitHub,
  и первый же комментарий к доковому PR красил его навсегда, а сторож слияния
  отказывал (2026-09-18). Два списка путей в файле обязаны совпадать.
- `ci` (или `<зона>-ci`, если зон несколько) — прогон тестов. Содержимое — стек
  проекта; канон фиксирует имя и то, КОГДА тесты бегут (ниже).
- Одно имя на обе вещи — запрещено: зелёный статус тогда означает разное для
  человека и для агента (docs/TEAM.md, «Два имени, не путать»). Проверяет
  `dev-process/bin/process-doctor`.

## Когда тестам бежать, а когда нет

Полный прогон на PR из одних `.md` не проверяет ничего. Правило: тесты бегут по
ПУТЯМ ДИФФА, а не по факту PR.

**Лишний прогон стоит не только минут** — и это решило вопрос «может, пусть
бегут всегда, так надёжнее». Измерено проектом на 1799 тестах (полный набор —
6 минут):

- **Очередь.** Self-hosted раннер обычно ОДИН — машина владельца. Лишний прогон
  занимает его целиком, и проверки живых PR стоят за ним. Четыре прогона подряд
  на merge'ах доковых правок парализовали конвейер на полчаса. На одном раннере
  «гонять всё всегда» даёт не надёжность, а очередь.
- **Ложный красный.** Прогон не нейтрален: на флейкующих тестах (там это были
  тайминговые — штрафная задержка входа, неразличимость времени ответа) два
  перезапуска подряд дали два РАЗНЫХ красных на неизменённом коде. Каждый лишний
  полный прогон — ещё и шанс разбирательства на пустом месте.
- **Цена сужения — ноль.** Доковый PR проходит гейт за 16–17 секунд вместо
  шести минут; PR, трогающий продукт, гонит полный набор как раньше. Про «или
  сам workflow» здесь раньше стояло «как раньше» — с 2026-09-20 это неправда,
  см. поправку про инертные джобы ниже.

Поэтому «`ci` на каждом PR» — НЕ инвариант канона. Инвариант один: тесты бегут
везде, где дифф трогает исполняемое. Сужение по путям — законное поведение, и
`process-doctor` поломкой его не считает.

- **Решает `dev-process/tools/pr-category.py --tests-needed`** — по той же
  таблице `docs/process/pr-category.tsv`, что и категорию PR, ПЛЮС поправка
  (ниже). Своей второй таблицы «безопасных путей» не заводи: две таблицы на один
  вопрос разойдутся, и разойдутся молча. Вывод — `tests=yes|no` в
  `$GITHUB_OUTPUT` и объяснение с путями в лог и summary: **пропуск обязан быть
  виден словами**, а не отсутствием шага.
- **Категорию PR инструмент при этом НЕ спрашивает, и это главное.** Категория
  отвечает «насколько дорога ошибка»: правка промпта роли рисковая, потому что
  дорого её проглядеть, — но прогонять там нечего, кода в ней нет. Решение
  принимается по путям: `.md`, `.txt`, `LICENSE` — текст, всё остальное
  (включая незнакомые расширения) — исполняемое, и на нём тесты бегут. Ошибаться
  полагается в сторону прогона. Первая версия правила спрашивала категорию и
  гоняла полный прогон на правке промпта — проект, где правило и родилось,
  исправил это раньше канона.
- **Джоба, которая тестов не гоняет, прогона не получает (решение PO
  2026-09-20).** `.github/workflows/gate.yml` (читает вердикт ревью) и
  `.github/workflows/hygiene.yml` (считает дифф) набором тестов не проверяются —
  он их не импортирует и не запускает. Список ЗАКРЫТЫЙ и живёт в
  `TESTS_INERT_WORKFLOWS` (`tools/pr-category.py`), а не шаблоном
  `.github/workflows/**`: шаблон унёс бы и джобу тестов, а она обязана
  прогоняться сама — сломанную джобу прогона нечем поймать, кроме её
  собственного прогона. Незнакомый workflow тесты гонит. `.github/scripts/**`
  остаётся исполняемым: там считается, бежать ли тестам. Условие возврата
  правила записано рядом со списком в коде: имя уходит из него, как только файл
  начнёт исполнять код продукта ИЛИ решать, бежать ли тестам.
- **Пропускается ШАГ тестов, а не workflow.** `paths-ignore` на джобе убрал бы
  её статус с PR целиком — а статуса ждут формула merge и branch protection,
  если его включат. Джоба бежит всегда, шаги — под `if:` по `tests`.
- **Fail-closed.** Дифф не посчитался или пуст — тесты бегут: минуты впустую
  дешевле незамеченной поломки.
- **Дифф, не трогающий исполняемое дерево, прогона не получает (решение PO
  2026-09-18).** Тот же `--tests-needed` пропускает прогон на `.py`-диффе, если
  дерево разбора совпало с базой PR вместе с докстроками (правка одних
  комментариев — байт исполняемого не изменился), либо разошлись только
  докстроки, а код проекта нигде не читает `__doc__`/`getdoc`/`pydoc`. Есть
  чтение — докстрока там данные, прогон бежит. Доказательство только машинное
  и печатается в summary; проект, вендорящий копию инструмента, обязан нести
  и эту проверку.
- **На `main` не гонять дерево, которое уже проверено на PR.** После squash
  ствол получает коммит, которого не было, — но если ветка была доведена до
  `main` перед слиянием, ДЕРЕВО у него то же, что у вершины PR, и зелёный
  прогон уже есть. Проверка в шаге решения на `push`: найти PR по коммиту
  (`gh api repos/<o>/<r>/commits/<sha>/pulls`), взять его `head.sha`, сравнить
  `git rev-parse <head>^{tree}` с `git rev-parse <sha>^{tree}` (вершина PR
  доступна и после удаления ветки — по `refs/pull/N/head`); деревья равны и
  `ci` на вершине PR зелёный (`gh api .../commits/<head>/status`) — пропуск с
  причиной в summary. Деревья разные — ветка отстала, ствол несёт комбинацию,
  которой не проверял никто: прогон нужен (спринт 09 одного проекта нашёл на
  дереве слияния пять ошибок, которых не было ни на одной из зелёных веток).
- **Останов на первом красном — там, где он не прячет информацию.** Локально у
  qa и исполнителя — всегда (`python -m unittest -f`, у других стеков — свой
  флаг): красное нужно увидеть, а не досмотреть. В CI — двумя ступенями:
  сначала модули, чьи имена совпадают с изменёнными файлами, с остановом на
  первом падении (красное за секунды, не через шесть минут); при их зелени —
  остальной набор БЕЗ останова, чтобы один прогон показал все падения, а не
  первое из них и «перезапусти». Выборку «только эти модули» это не заменяет:
  она требует карты «тест → код», которой нет, а угаданная выборка хуже
  полного прогона — зеленеет, не проверив. Само время прогона чинится в
  тестах: шесть интеграционных наборов, ждущих по стенным часам, дают две
  трети прогона одного проекта (правило — роль qa).
- **На push в main пути разбираются ТОЖЕ** — сравнивать есть с чем:
  `github.event.before` это вершина до пуша. Первая редакция гоняла на push
  всегда «потому что сравнивать не с чем», и каждый merge доковой правки стоил
  полный прогон — за вечер так сгорело четыре подряд. Первый пуш ветки и
  переписанная история дают пустой или нулевой `before`: тогда прогон нужен,
  судить не по чему. Ручной запуск (`workflow_dispatch`) гоняет всегда — его
  зовут именно затем, чтобы прогнать.
- На GitHub-hosted раннере канона на диске нет: там проект вендорит копию
  инструмента в свой `.github/scripts/` и сверяет её с каноном. На self-hosted
  у владельца канон лежит рядом и зовётся напрямую.

## Раннер джоб — выбор проекта

GitHub-hosted `ubuntu-latest` не зависит от сна машины владельца, но тратит
минуты GitHub и ставит чужой интерпретатор. Self-hosted у владельца даёт ровно
тот интерпретатор, под который писан проект, и минут не тратит, но раннер
оффлайн = прогон стоит в очереди и статус не появляется. Канон не выбирает за
проект; решение и его дату запиши в свой стек-файл.

**Self-hosted — первоклассный случай, а не экзотика, и у него своя арифметика.**
Раннер там обычно один, то есть параллелизма нет: прогоны выстраиваются в
очередь, и цена лишнего измеряется не минутами счёта, а простоем живых PR. Ещё
он ближе к живой машине владельца, чем чистый образ, поэтому там раньше вылезают
тайминговые тесты, зелёные на GitHub-hosted. Оба следствия — довод сужать прогон
по путям, а не гонять всё подряд.

## PR, вносящий сам gate.yml (самозагрузка гейта)

К ветке по умолчанию привязаны только триггеры `issue_comment` и
`workflow_dispatch` — автоматический пересчёт статуса «по новому комментарию»
на таком PR не сработает, пока gate.yml не в main. Событие `pull_request` при
этом исполняет версию ИЗ ВЕТКИ, поэтому статус получается так: оставить
вердикт, затем `gh run rerun <id>` последнего прогона джобы — он перечитает
комментарии живьём и позеленит `gate` без нового коммита. Если раннер
недоступен и путь закрыт — такой PR принимает оркестратор по
вердикту-комментарию code-reviewer.

## Merge и вердикты

- **Merge — только `bin/merge-green.sh <N>`, прямой `gh pr merge` не применять.**
  Required status checks на приватном репозитории free-плана недоступны, то есть
  зелёное состояние держала ПАМЯТЬ того, кто жмёт merge, — и однажды не удержала:
  PR уехал в main при красной проверке. Скрипт читает `gh pr view --json` и
  `gh pr checks --json` и отказывает по одной строке на причину. Эталон —
  `dev-process/templates/merge-green.sh`, копия проекта — `bin/merge-green.sh`.
  `DRY_RUN=1` печатает решение, не сливая.
- Формула стадий (кому APPROVE и PASS положены) остаётся за manager'ом —
  docs/TEAM.md «Риск-ориентированный конвейер»; скрипт проверяет ЗЕЛЁНОЕ, а не
  состав стадий. SHA вершины сверяй через `gh pr view --json headRefOid`.
- Контракт вердикта гейта — три первые строки комментария:
  `GATE: APPROVE|BLOCK` + `sha: <headRefOid>` + `role: code-reviewer|оркестратор`
  (docs/TEAM.md «Контракт вердиктов»). Без sha-строки вердикт не засчитывается
  ни workflow, ни метриками; без role-строки — джобой. Матч в джобе привязан к
  ПЕРВОЙ строке: свободный поиск якоря по телу комментария зеленит статус на
  любом его упоминании — например в BLOCK'е, который объясняет, чего не хватило
  для APPROVE.
- **«Не автор» проверяется одним из двух способов — `AUTHOR_CHECK` в шапке
  джобы.** `login` (умолчание эталона): комментарии учётной записи автора PR
  отбрасываются — работает там, где у ролей разные аккаунты. `role`: считается
  роль третьей строки вердикта — для проекта, где все агенты ходят одним
  аккаунтом владельца: там сравнение логинов отбрасывает настоящий вердикт и
  гейт не зеленеет никогда (найдено 2026-09-14). Строка `role:` ловит случайный
  самоштамп и не ловит осознанную ложь роли; машинной защиты от неё на одном
  аккаунте нет, защищает свежий инстанс ревьюера с другим методом чтения.
  Единственный путь к машинной проверке — отдельный аккаунт или токен для
  ревьюера, и это решение PO (цена — управление секретами).
- **Дифф без изменения поведения обряда не получает.** Правка одних докстрок и
  комментариев в `.py` доказуема: `dev-process/tools/pr-category.py` сверяет
  дерево разбора против БАЗЫ PR (не промежуточной вершины — автор однажды
  сверил не с тем) и печатает «непродуктовый» с доказательством. Шаг эталона
  `gate.yml` зовёт инструмент сам (вендоренная копия
  `.github/scripts/pr-category.py` или канон рядом на self-hosted раннере) и при
  доказательстве ставит `gate` зелёным без вердикта (решение PO 2026-09-19);
  нет инструмента на раннере — гейт закрывает оркестратор вердиктом
  `role: оркестратор` с выводом инструмента в теле. Тесты — по правилу выше.
  Для языков без разборщика в stdlib доказательства нет — категория по путям.
  Докстроку, которую код читает через `__doc__`, инструмент считает данными и
  прогон не снимает; на категорию это не влияет.

## Учёт дефектов и канарейки

- Баг, найденный ПОСЛЕ merge, — `gh issue create --label escaped-defect
  --body-file <файл>`: это вход метрики улова гейта; без привычки третье
  число метрики всегда ноль и врёт.
- Канареечный PR (синтетический дефект для проверки чувствительности гейта)
  помечается меткой `canary` — метрики процесса такие PR исключают.
