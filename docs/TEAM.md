# Команда агентов

> **Канон этого документа живёт в репозитории процесса** — `dev-process/docs/TEAM.md`
> (по умолчанию `~/Coding/Pet/dev-process`). Копия в проекте существует потому,
> что агент читает только внутри своего рабочего каталога. Правишь одну — правь
> обе; расхождение показывает `dev-process/bin/process-doctor`.

Роли агентов:

- **Источник правды:** `.claude/agents/*.md`
- **Зеркало для Cursor:** `.cursor/agents/*.md`

При правке роли обновляй ОБА каталога (копированием содержимого); Cursor Task не
принимает `subagent_type` — передай текст роли в промпт `generalPurpose`.

Продукт-овнер — человек: формулирует задачи (часто с `analyst`) и делает всё, что
требует человека (логины, секреты, внешние аккаунты, VPS). Поведение главной
сессии (оркестратора) — канон `roles/orchestrator.md`: шесть обязанностей и
протокол смерти. Конвейер спринта ведёт `manager`.

## Спринты (виртуальный Scrum, решение PO 2026-07-16)

Работа идёт спринтами. Спринт = раунд команды с ОДНОЙ конкретной целью-ценностью
(формат: «после спринта PO может …»; спринт уборки — через отрицание, форма — шаблон
паспорта). Паспорт — docs/sprints/SPRINT-NN.md: цель, скоуп, DoD, вне-скоупа, Точки
PO (R3, см. ниже) и ТРИ ВОПРОСА входа каждой порции (полный путь · повод · чем
измерим — шаблон паспорта: порция без ответов не входит, даже если код написан);
сверка записей очереди перед КАЖДЫМ пакетом — часть его DoD (docs/rules.md «Запись
очереди»); живой гейт, принятый неглядя два спринта подряд, уходит из DoD (шаблон,
«Live-гейты»). Скоуп-фриз: новые вводные PO — в
docs/specs/BACKLOG.md (мелочь — меткой `chore` в chore-очередь, R3), разбираются
на планировании следующего спринта (в текущий — только блокеры решением PO).
По завершении в паспорт дописываются «Отчёт спринта» (цель достигнута y/n, чейнджлог,
метрики, что уехало в бэклог) и «Ретро» (1–3 процессных наблюдения).

Чеклист оркестратора на границах спринта. При закрытии: напомнить PO про
self-hosted раннеры (их список и команды — в AGENTS.md проекта); уборка —
контейнеры тест-БД агентов и отработавшие worktree (`git worktree prune` +
чистка .claude/worktrees; правила уборки — стек-файлы); `./scripts/reap-stale.sh`,
если он в проекте есть (dry-run → apply); `./scripts/process-metrics.sh` — улов гейта
и латентности в ретро (вход — issues `escaped-defect`; их заводит нашедший баг
после merge); полный проход `docs` по всему дереву (см. «Документация»); открытые строки
CONFLICT в BACKLOG (второй раз не закрылась — блокирующая точка PO);
надзор застоя `dev-process/tools/process-watch.py`; канареечный PR (метка
`canary` — см. «Обязательное ревью»); при накопленном журнале — `meta-reviewer`
(дельты из фактов, предохранитель ≥3; он же пополняет PRECEDENTS из утечек).
Спящие условия (аудит №4): голдсет пуст / базовая линия не снята / надзор не в
тике — первый непустой пункт уходит PO неблокирующей точкой, сами не наступят.
При старте: проверить раннеры online; поднять версии продуктов первой задачей
волны (механика бампа — README/стек проекта).
Ретро включает ритуал гигиены канона (решение PO 2026-08-28): правило,
соблюдаемое и без текста, — удалить; правило, переведённое в хук, — удалить из
прозы; регламент толще ~400 строк — сигнал сжимать, а не дописывать.
На груминге следующего спринта оркестратор ЧИТАЕТ секцию «Ретро» прошлого
паспорта — ретро пишутся для этого читателя, не в архив.

## Как это работает (схема R2, решение PO 2026-07-18)

```
PO ↔ оркестратор — PO-интерфейс: спека (analyst), рисковые приёмки, границы спринтов
        ↕ вехи (PR создан / qa PASS / merge / блокер)
     manager — исполнительный конвейер спринта по готовой спеке
        → исполнители (worktree) → qa → docs → merge нерисковых PR
```

Мотив (R2): в R1 оркестратор совмещал диспетчеризацию с PO-интерфейсом и отвечал PO
с задержкой; рутина ушла `manager`'у с уроками R1 в роли. Рисковые PR manager
эскалирует оркестратору. Откат: клины менеджера вернулись — назад к R1. Точечные
правки — только chore-полосой (R3).

- **Analyst-gate:** сначала `analyst`, ЕСЛИ требования ещё не существуют в нормативке
  (`Approved` → дальше; `Blocked`/`Needs rework` — к PO). Гейт пройден автоматически,
  когда возможность уже покрыта S-кодами спека / ревью-картой / паспортом с явным DoD —
  повторная формулировка требований запрещена экономией.
- **Гейт плана — заготовка (включается решением PO после docs/baseline.md):** план
  волны ревьюит СВЕЖАЯ сессия по `dev-process/templates/PLAN-REVIEW.md`; до
  включения — по запросу PO на рисковых волнах.
- Исполнители работают в worktree-изоляции, ветка пушится после каждого коммита,
  отчёт — ТОЛЬКО финальным сообщением (SendMessage «вбок» между агентами не работает).
- **Инвариант ветки порции (введён 2026-07-26, инцидент С32-S4):** ветку резать от
  `origin/main` (локальный main в чекауте PO отстаёт) и сразу проверить одной
  строкой, что `git -C <слот> merge-base origin/main HEAD` непуст. Shallow-fetch
  режется хуком; чем он смертелен именно здесь — docs/stack/github.md.
- **Фриз ствола — main не пересобирается под ждущим PR (2026-07-26, урок С32-S4;
  НЕ путать со скоуп-фризом — тот защищает объём спринта):** пока рисковый PR стоит
  на приёмке оркестратора, коммиты в `main` ЖДУТ — ни CHANGELOG, ни chore (полоса
  тоже стоит), ни уборки: каждый пуш в `main` рождает ребейз ждущей ветки, новый
  вердикт гейта (он per-SHA) и новый прогон CI (#233 ребейзился трижды из-за одного
  BACKLOG). Под фризом manager закрывает вехи ЛОКАЛЬНЫМ коммитом STATUS без push,
  батч после снятия (аудит №4). Снимает держатель приёмки; страховка — manager сам
  по факту `gh pr view --json state,mergedAt`; фриз старше 4 часов без движения —
  блокирующая эскалация PO.
- Ход агента не длиннее ~10 минут без промежуточного финального прогресс-отчёта;
  долгие сборки — только с явным timeout.
- **Имя долгоживущего агента — роль и срок жизни** («менеджер спринта 11»), не
  первая задача: панель показывает имя при рождении, и закрытая работа час висела
  как идущая (правило PO 2026-09-18). Имя по задаче — агента не переиспользуют.
- **Файл прогресса (решение PO 2026-08-28):** порция длиннее пары часов ведётся с
  `PROGRESS.md` в worktree (сделано / отменено-и-почему / решено / открыто) — он
  переживает обрыв и сжатие контекста. Пункт, не закрывшийся с трёх попыток,
  помечается «заблокирован: причина», исполнитель идёт дальше — одна нерешаемая
  задача не съедает окно тихого прогона.
- Мелочь идёт chore-полосой manager'а (R3), не через оркестратора.
- Агенты стартуют с чистым контекстом: общая память — `docs/` и git-история.
  Исполнители обновляют свои доменные доки; `docs` ловит расхождения и дыры.

## Схема R3 (пилот 2026-07-21, принята 2026-08-28)

Надстройка над R2 (конвейер manager'а сохраняется). Мотив: оркестратор был очередью
для мелочи, состояние конвейера жило в его памяти, касания PO были размазаны.
Статус: ПРИНЯТА решением PO 2026-08-28 — ~30 спринтов пилота без отката
(вопрос поднял аудит №4). Три изменения:

1. **Chore-полоса вместо «точечных правок в обход».** Мелочь (не трогает архитектуру,
   инварианты, миграции, контракты ядра и UI — UI требует живой проверки PO, это идея
   с точкой PO) оркестратор помечает `chore` в BACKLOG; manager ведёт её ПАРАЛЛЕЛЬНО
   волне: WIP ≤2, worktree, PR → зелёный CI → merge менеджером без qa (решение PO
   2026-08-08). Сомнение «мелочь ли» = не мелочь. Полоса вне скоуп-фриза, но фриз
   СТВОЛА останавливает и её.
2. **STATUS-борд** — `docs/STATUS.md`, единственный источник «что происходит сейчас»
   (спринт и цель, активные задачи с владельцами, последние вехи, дальше). Ведёт manager
   (узкое Write-исключение на этот файл; оркестратор — на границах спринта); обновление
   борда — часть определения вехи, включая коммит и push этого одного файла (под фризом
   ствола — без push). Ограничение «только docs/**» держится текстом роли; правка КОДА
   manager'ом = немедленный откат к R2. Сокращения порций (H, Del, C1∥C2): первая
   встреча — легенда в паспорте и строка в STATUS, в чате с PO — с расшифровкой.
3. **Точки PO + тихий автостарт.** Паспорт получает секцию «Точки PO» — исчерпывающий
   список ручных включений PO, объявленный НА СТАРТЕ; каждая точка — **блокирующая**
   (держит критический путь — эскалация немедленно) или **неблокирующая** (батчем).
   Спринт, где все точки закрыты и CI зелёный («тихий»), закрывается по чеклисту, и
   оркестратор автоматически стартует следующую волну SPRINT-PLAN с асинхронным
   дайджестом PO (нет активной сессии — нет автостарта). Предохранители (любой → стоп
   и вопрос PO): (а) утверждённых волн не осталось; (б) следующая волна
   рисковая/стратегическая — только явный «go» PO; (в) прошлый спринт «цель не
   достигнута»; (г) спринт трогал UI — live-проверка PO обязательна, такой спринт
   «тихим» не бывает; (д) self-hosted runner offline — волна без CI не стартует.

**Уровни процесса** (событие закрывается на самом низком достаточном уровне; вверх идут
только решения, не работа; за состояние уровня отвечает его артефакт, не агент):
L0 продукт (PO: ROADMAP, пивоты, go-live) → L1 план (оркестратор готовит, PO утверждает:
BACKLOG, груминг, SPRINT-PLAN) → L2 спринт (оркестратор: границы, спека, точки PO, рисковые
приёмки; паспорт) → L3 конвейер (manager: задачи, вехи, merge нерисковых, chore, STATUS) →
L4 исполнение (dev/qa/docs: worktree, PR, CI). Параллелизм живёт на L3–L4,
последовательность решений — на L0–L2.

**Backlog grooming (по запросу PO):** сверка «доки = код» (пометить СДЕЛАНО/мёртвое) →
кластеризация идей в темы-волны («после спринта PO может …») → развилки PO отдельным
списком → черновик нового SPRINT-PLAN → утверждение PO (фиксируется в шапке плана);
старый план помечается устаревшим.

**Критерий отката R3:** STATUS протух >1 раза за спринт (расхождение борда с фактом
git/PR/CI), manager заклинил обе полосы или выросла латентность решений PO — откат к
R2. Автостарт не проверен ни разу (С21 и позже).

## Риск-ориентированный конвейер (решение PO 2026-07-26)

Полный аппарат на каждую мелочь — главный источник расхода: 4-5 агентов на один PR упрутся
в лимиты раньше, чем в качество. Стадии подбираются по риску и размеру.

| PR | Стадии | Кто мержит |
|---|---|---|
| **Непродуктовый** (инфра-конфиги CI · доки · спайки · чисто тестовые диффы) | зелёный CI, БЕЗ ревью-гейта и qa (решение PO 2026-08-08); тесты — по путям диффа, см. ниже | manager |
| **Мелкий продуктовый** (< ~50 строк, нет риск-триггеров) | `code-reviewer` | manager |
| **Обычный продуктовый**: фича/фикс в одной зоне | `code-reviewer` + `qa` (параллельно, в одном ходу) | manager |
| **Рисковый по триггеру**: миграции · инварианты внешнего API · контракты ядра · auth/токены · нормативка и промпты ролей | `code-reviewer` + `qa` + **приёмка оркестратора** + фриз ствола; дифф из одних текстовых файлов (`.md`) — БЕЗ `qa`: принимать по DoD нечего, прогонять нечего | оркестратор |
| **Рисковый только по пути** (файл из таблицы, триггера нет) | `code-reviewer` + `qa`, как обычный продуктовый; без приёмки и фриза (решение PO 2026-09-19) | manager |

Почему на мелком хватает одной стадии: тесты и линт уже гоняет CI — `qa` там дублирует
машину. По той же причине её нет на ТЕКСТОВОМ рисковом диффе (регламент, промпт роли):
ревью обязательно — ошибка в промпте дороже ошибки в коде, — а приёмке нечего
запускать; считает `tools/pr-category.py`. Ревью-гейт не снимается с ПРОДУКТОВОГО кода: он ловит то, чего CI не видит.

Два потолка (решение PO 2026-08-28): продуктовый дифф больше ~400 изменённых строк
без обоснования размера в теле PR — основание для BLOCK «разбей PR»; третий подряд
НЕСОШЕДШИЙСЯ BLOCK по одному PR — эскалация techlead/оркестратору с обеими позициями,
а не новый круг. Круг сошёлся, если его находка признана и закрыта, а новая — другая
и мельче (три BLOCK подряд дали три разных дефекта, каждый мельче, — эскалация была
бы ошибкой, 2026-09-18); не сошёлся — повтор находки или спор «дефект ли это».
Счёт — по комментариям PR фактом (свежий инстанс «своего третьего» не имеет — аудит
№4); «подряд» = без промежуточного APPROVE, переиздания после чистого ребейза не
считаются. Круг правок по неблокирующим находкам — один; остаток строкой в BACKLOG.

**Категорию считает инструмент, суждение только повышает (решение PO 2026-08-28).**
Первый шаг — `dev-process/tools/pr-category.py --project .`; его вывод это ПОЛ,
понижать нельзя. Чего он не видит — семантические риск-триггеры (миграции,
инварианты внешнего API, контракты ядра, auth): их добавляет суждение, вверх.
**Приёмку оркестратора и фриз ствола назначает триггер, а не путь (решение PO
2026-09-19):** «рисковый» из таблицы путей значит «ревью и qa обязательны», а
третье чтение и остановка ствола — только когда manager назвал триггер в PR.
За день приёмка не поймала ничего и раз ошиблась в плюс, а три блокирующие
находки дал ревьюер; на миграции базы с медданными третье чтение остаётся.
**Обряд назначается по природе диффа, а не по имени файла (2026-09-18):** дифф из
одних докстрок и комментариев, для которого инструмент доказал неизменность
поведения сверкой дерева разбора против базы PR, — непродуктовый, какой бы путь ни
трогал: тесты бегут, а статус `gate` джоба ставит зелёным САМА — шаг эталона
`gate.yml` зовёт инструмент и при доказательстве вердикта не ждёт (решение PO
2026-09-19; на раннере без инструмента — обычный вердикт). Иначе правка слова в
рисковом файле и порция на двести строк в нём же идут одним путём. Доказательство
только машинное; языки без разборщика его не получают.

**Адверсариальная приёмка оркестратора начинается с трёх вопросов (решение PO
2026-08-28)** — свежему инстансу, не автору (автор свой отчёт защищает), ДО чтения
отчёта: (1) что происходит от входа данных до изменения в системе; (2) три места,
где сломается; (3) что решено самостоятельно, чего не просили. И метод: проверяй
вопрос, а не токен — прежде чем подтвердить утверждение, назови, как ещё оно могло
бы быть ложным, и поищи вторым способом (семь ошибок за день у четырёх участников
имели этот корень; ловил каждый раз другой читатель с другим методом).

Клиентский UI — отдельно: он не мержится на «CI зелёный + юнит-тесты» (правило
`verify-client-ui-before-merge`: живой взгляд PO; известные классы дефектов закрывает
XCUITest по a11y-ID); ревью-гейт при этом всё равно обязателен.

## Обязательное ревью (три разные вещи, не путать)

- **Ревью-гейт диффа — `code-reviewer`, на каждый продуктовый PR** (непродуктовые —
  без гейта, матрица выше). Спавнится **свежим инстансом**: не писал этот код, читает
  дифф из git сам, **не форк беседы автора** (форк унаследует рассуждения автора и
  вернёт ту же ошибку с уверенным лицом). Вердикт — комментарием в PR с привязкой к
  SHA вершины; джоба `gate.yml` выставляет commit status `gate`. Новый push = новый
  SHA = нужен новый вердикт; чистый ребейз/дописанные тесты — сокращённый разбор по
  `git range-diff` со ссылкой на прежний (решение PO 2026-08-08).
- **Приёмка по DoD — `qa`.** Сделано ли заказанное, зелены ли прогоны, покрыто ли
  тестами. На обычном и рисковом PR merge требует ОБОИХ: PASS `qa` и APPROVE гейта.
- **`reviewer` — периодический, отчётный, НЕ гейт**: модули целиком между волнами,
  отчёт в `docs/reviews/`, merge не блокирует.

**Контракт вердиктов машиночитаем (решение PO 2026-08-28).** Гейт — первые строки
комментария `GATE: APPROVE|BLOCK` + `sha: <headRefOid>` + `role: code-reviewer|оркестратор`
(читают gate.yml, метрики, журнал) и ТЕ ЖЕ строки в финальном сообщении (журнал
видит транскрипт, не PR); qa — первой строкой отчёта `QA: PASS|FAIL`. Вердикт прозой
журнал считает эвристикой — якорь обязателен. **Штамп ставит НЕ автор:** вердикт
вправе оставить только `code-reviewer` или оркестратор (осознанное закрытие гейта с
указанием правила). Как джоба проверяет «не автор» — по учётной записи автора PR
или по строке `role:` там, где все агенты ходят одним аккаунтом владельца
(`AUTHOR_CHECK` в эталоне; граница честно — docs/stack/github.md). Зелёный `gate`
обязан означать «смотрел не автор» — прецедент: роль штампанула собственный PR,
статус позеленел.

**Два имени, не путать: `gate` — вердикт ревью, `ci` — тесты.** `gate` это commit
status, который джоба `gate.yml` выставляет ПО КОММЕНТАРИЮ `code-reviewer` (эталон
джобы — `dev-process/templates/gate.yml`, расхождение ловит доктор): тестов она не
гоняет и на непродуктовых PR не бежит — вердикта там не бывает, это норма.
Тесты — отдельная джоба `ci` (или `<зона>-ci`), и **бегут они по ПУТЯМ ДИФФА, а не
по факту PR**: полный прогон на PR из одних `.md` — чистая трата. Считает
`tools/pr-category.py --tests-needed`; механика, ловушки, цена лишнего прогона и
порядок прогона — docs/stack/github.md. Зелёный `gate` молчит о тестах, зелёный `ci`
— о ревью; формула merge требует оба, и назвать `gate` прогоном тестов — ровно то
противоречие, ради которого правило записано.

**Ограничение механики (честно):** required status checks недоступны (приватный
репозиторий, free-план) — красный `gate` merge не блокирует; зелёное держит
`bin/merge-green.sh`, ценность статуса — аудируемость (раннер и самозагрузка
gate.yml — docs/stack/github.md).

**Улов гейта проверяется числами, а не ощущением:** на ретро — `process-metrics.sh`
(влито / заблокировал / утекло; медианы «PR → вердикт», «вердикт → merge»). Пороги:
первый вердикт позже 2 ч и merge позже 4 ч после вердикта (часы РАБОТЫ; 4 ч — та же
граница, что у фриза ствола) разбираются на ретро, второе подряд превышение —
эскалация PO. Баги после merge — issue `escaped-defect`. Гейт не блокировал ничего,
а утечки есть — чиним промпт `code-reviewer`, не добавляем стадии.

**Чувствительность — канарейкой, правка гейта — голдсетом (решение PO 2026-08-28).**
На границе спринта оркестратор подаёт канареечный PR (синтетический дефект из прошлых
утечек, метка `canary`; метрики её исключают); пропуск — issue `canary-miss` + строка в
«Отчёте спринта»: молчание гейта должно быть событием. PR, меняющий роль
`code-reviewer`, не вливается без прогона голдсета (`templates/GOLDSET.md`).

## Документация (обязанность `docs`)

**Когда запускается `docs` (решение PO 2026-08-28):** manager — после merge каждого
обычного/рискового продуктового PR (сверка затронутых доков + CHANGELOG, пушит docs
сам); оркестратор — полный проход на границе спринта (дрейф «доки = код» по всему
дереву; он же закрывает накопившиеся мелкие PR и chore). Прежний триггер «значимый
инкремент» отменён как толкуемый по памяти.

**Правила текста (решение PO 2026-08-28):** метку «решение PO <дата>» ставит только
человек — всё непомеченное в docs/ считается текстом агентов, новая метка без
источника — находка docs-агента. **Правило живёт в ОДНОМ файле; второй документ
на ту же тему ССЫЛАЕТСЯ, а не пересказывает** — пересказ и есть механизм, которым
две нормы расходятся. То же — факт с датой (переезд, деплой, включение): источник
один (CHANGELOG; для спринта — паспорт), остальные ссылаются или дату не называют. Противоречие документов не разрешается молча: побеждает
самый свежий датированный, конфликт — строкой CONFLICT в BACKLOG (формат,
владелец и срок — в шапке той секции; строка без владельца не заведена).
Отменённые по ходу решения — в секцию «Отменено» паспорта (что · почему · условие
пересмотра): без записанной причины отвергнутое воскресает после сжатий контекста.

Перечень и владение доками — ПРОЕКТНЫЕ (карта — AGENTS.md проекта; таблица
владения — roles/docs.md). Канон фиксирует обязательный минимум: README,
CHANGELOG (ведёт docs), docs/STATUS.md (ведёт manager), паспорта спринтов,
docs/specs/BACKLOG.md.

**Вход работы — `docs/specs/BACKLOG.md`**, а правило про него — норма и живёт
отдельно: `docs/rules.md` → копия проекта `docs/process/RULES.md` (критерий «куда
писать», второй трекер, формат CONFLICT). Почему врозь — docs/boundary.md.

## Git — модель «ветки + PR» (решение PO 2026-07-16)

- Код пишется в ветках задач: `task/<короткий-слаг>` (одна ветка на блок/возможность).
- На `pull_request` запускаются component workflow по затронутым path-фильтрам;
  manager создаёт PR (`gh pr create`), а СЛИВАЕТ только `bin/merge-green.sh <N>`
  (эталон — `templates/merge-green.sh`): required checks на free-плане недоступны,
  и зелёное держала память — однажды не удержала. Состав стадий по-прежнему за
  manager'ом: APPROVE + PASS (где положен) + зелёный PR-CI, всё на вершине ветки.
- Прямые пуши в main — только для docs/**, *.md, .claude/**, .cursor/**; прямой
  пуш КОДА в main запрещён регламентом.
- Push веток CI не запускает; релизные теги (`server-v*` / `client-v*`) запускают
  сборочные workflow; каждый доступен и через `workflow_dispatch`.
- Подпись `Co-Authored-By: Claude …` в коммитах не ставится (решение PO
  2026-09-18): её подставляет харнесс, а не процесс — docs/rules.md «Сообщение
  коммита».
- Force-push и правка опубликованной истории запрещены агентам ВСЕГДА (режется
  хуком); человеку разовое переписывание приватного репозитория — отдельным
  решением PO с процедурой в docs/ (решение PO 2026-08-28; прецедент —
  docs/history-rewrite.md). «После пуша дождись зелёного» живёт на PR.

## Жёсткие зоны (enforcement, решение PO 2026-07-17)

Зоны ответственности обеспечиваются ИНСТРУМЕНТАМИ, а не только текстом ролей:

- **Правило → хук (решение PO 2026-08-28):** запрет, переведённый в механический
  хук (`dev-process/hooks/`, подключается в settings.json проекта руками PO), из
  прозы ролей УДАЛЯЕТСЯ — две реализации разъедутся (в каноне до подключения хука
  во всех проектах реестра остаётся строка-ссылка без повтора формулировки). Хук
  обязан возвращать причину запрета в сессию: молчаливый отказ учит обходить.
- **manager** — НЕ кодит: Sources/, Client/, Tests/, скрипты, конфиги — нарушение
  зоны. Write/Edit только в docs/**; Bash — проверка фактов, git-операции приёмки,
  commit/push docs-путей; остальное — координация.
- **Правки docs/** — docs-агент И manager (решение PO 2026-07-21); за сверку
  «доки = код» и CHANGELOG отвечает docs-агент; `docs/STATUS.md` — только manager.
- **Приёмка PR**: qa выносит вердикт и МОЖЕТ добавлять только тесты; правки
  продакшен-кода — ВСЕГДА возврат автору или новый исполнитель. Механический
  rebase без семантических конфликтов допустим принимающему; семантический
  конфликт = возврат автору.
  **Прогоны приёмки — в worktree автора (С28-P2, одна сборка на порцию):** qa
  гоняет прогоны в прогретом дереве автора (автор остановлен, передачу подтверждает
  manager); код там НЕ правит и ветку НЕ пушит — только читает и запускает. Свои
  правки (включая тесты) — обычный режим в собственном worktree. Экономия стадий
  сборки — стек-файлы.
- **Merge**: нерисковые PR и chore — manager по формуле конвейера; рисковые —
  оркестратор после адверсариальной приёмки. Push релизных тегов — исполнитель
  приёмки после PASS (или оркестратор).
- **Прогоны субагентов — только синхронные (С28/P-4):** фоновые задачи исполнителям
  запрещены; сборки/тесты форграундом с timeout; финал — результат, не «жду».
  Manager запускает детей run_in_background=false. Сборок ≤2 одновременно (С28/P-3).
- Диф PR обязан соответствовать зоне автора: нарушение зоны = автоматический FAIL
  приёмки.

## Владение задачами (после инцидента двойной приёмки PR #6)

- У каждой задачи ровно ОДИН владелец (owner в TaskList). Приёмка PR — всегда manager.
- Перехват задачи — только после подтверждённой отмены у прежнего владельца
  (TaskUpdate + его ответ, что остановился). «Запустил своего параллельно на
  всякий случай» — запрещено: двойная работа и токены впустую.
- Оркестратор при простое сначала пинает владельца фактами; перехватывает, только
  если владелец не ответил/мёртв.

## Техдиректор (`techlead`, решение PO 2026-07-23)

Владеет нормами и технологическим выбором; НЕ кодит и НЕ дублирует enforcement
(стандарты проверяют code-reviewer/reviewer/qa по чеклистам, которые актуализирует
techlead). Точки включения:

- **Обязательно**: новая зависимость / смена подхода / bump минимальных версий →
  ADR в docs/adr/ ДО внедрения. Ответственность за выбор — у techlead в рамках
  ограничений PO; дорогое/стратегическое/необратимое — эскалация PO.
- По запросу: ресерч решений, техническая виза спеки, арбитраж споров
  dev ↔ reviewer/qa.
- Аудит стандартов — на границе спринта или по запросу.
